# RISK-ZERO 운영·데이터·위험 대응 정책 (초안)

- **문서 소유:** Pixel-Zero 팀
- **적용 대상:** 웹 모니터링 · 모바일 MVP · 데이터 API · D1 데이터베이스
- **버전 / 기준일:** v0.2 / 2026-07-23
- **상태:** 팀 검토용 — 외부 실증 전 재승인 필요

> [!NOTE]
> **이 문서의 성격**
>
> 이 문서는 대학 캡스톤 디자인 MVP를 개발하고 시연하기 위한 팀 내부 기준이다. 법률 자문이나 실제 서비스의 개인정보 처리방침, 영상정보처리기기 운영 방침을 대신하지 않는다.

## 핵심 정책 요약

- **보조 시스템:** RISK-ZERO는 위험을 확정하는 장치가 아니다. 현관에서 이상 신호가 들어왔을 때 거주자와 보호자가 상황을 더 빨리 확인하도록 돕는다.
- **사람의 확인:** 알림을 확인하고 신고 여부를 결정하는 주체는 사람이다. 위험 점수만으로 신고나 출입 제어를 자동 실행하지 않는다.
- **최소 수집:** 현관 안전에 필요한 센서값만 받는다. 영상과 얼굴인식은 현재 단계에서 사용하지 않는다.
- **데모 분리:** 현재 화면의 4단계와 점수는 실행 흐름을 확인하기 위한 더미 데이터다. 실제 안전 판단이나 성능 주장에는 사용하지 않는다.

### 현재 MVP 경계

| 현재 구현 | 아직 구현하지 않음 / 외부 실증 전 필수 |
| --- | --- |
| D1 더미 데이터, 센서 이벤트 API, 사고·장치 조회 API | 사용자·장치 인증, 장치 서명, 재전송 공격 방지 |
| 웹 모니터링 및 모바일 MVP 화면 | 실제 푸시·문자·전화·112 신고 연동 |
| 고정 더미 점수와 4단계 상태 표시 | 검증된 위험도 산식, 임계값, 모델 버전 |
| 영상 수집 비활성 | 카메라 설치 적법성 검토, 안내판, 별도 영상 운영 방침 |

## 1. 목적과 적용 범위

이번 프로젝트에서는 현관 주변의 센서 신호를 같은 형식으로 모으고, 거주자와 보호자가 상황을 확인할 수 있는 흐름을 만든다. 이 정책은 웹 모니터링 화면, 모바일 MVP, 데이터 API, D1 데이터베이스, 앞으로 연결할 센서 게이트웨이와 위험도 엔진에 적용한다.

현재 초안은 대학 캡스톤의 개발·시연 범위를 기준으로 작성했다. 실제 거주지에서 장기간 운영하거나 영상 촬영, 자동 신고, 도어락 제어를 시작하려면 개인정보 처리 근거와 설치 공간, 학교 지침, 장치 안전성을 다시 확인한 뒤 정책을 개정한다.

## 2. 기본 원칙

| 원칙 | 적용 기준 |
| --- | --- |
| 안전 우선 | 위험 알림을 놓치는 것과 정상 상황을 계속 위험으로 알리는 것 모두 문제가 된다. 두 오류를 함께 보고 사람이 확인하는 절차를 둔다. |
| 인간 감독 | 점수만으로 신고, 출입 제한, 신원 추정 같은 중대한 조치를 자동 실행하지 않는다. |
| 목적 제한 | 현관 안전 확인과 시스템 검증에 필요한 범위에서만 데이터를 사용한다. |
| 최소 수집 | 원본 영상과 신원정보보다 수치형 센서값, 구간값, 비식별 이벤트를 우선한다. |
| 설명 가능성 | 결과마다 입력 시간, 사용 요소, 엔진명·버전, 상태를 남겨 나중에 같은 판단을 확인할 수 있게 한다. |
| 공정성과 존중 | 성별, 인종, 장애, 외모, 의복, 추정 감정처럼 행동과 무관하고 편향 가능성이 큰 특성은 위험요소로 쓰지 않는다. |

## 5. 센서 데이터 수집 정책

### 5.1 허용되는 데이터

센서 종류는 앞으로 바뀔 수 있다. 그래서 각 장치의 원본 데이터는 공통 SensorEvent 구조로 변환한다. 관측값은 metric, 값, 단위, confidence, quality, captured_at으로 정리하고, 새로운 센서는 DB 컬럼을 계속 늘리는 대신 metric을 추가하는 방식으로 연결한다.

| 범주 | 예시 | 사용 목적 |
| --- | --- | --- |
| 접근·체류 | presence, dwell_seconds, min_door_distance_cm, approach_count | 현관 접근의 지속성과 반복성 확인 |
| 충격·문 상태 | impact_peak, impact_count_10s, door_state, door_open_seconds | 강제 개방 또는 반복 충격의 단서 |
| 사용자 요청 | manual_sos | 거주자가 직접 긴급 상황을 알린 여부 |
| 품질·합의 | sensor_agreement_count, confidence, quality | 단일 센서 오류와 복수 센서 일치 여부 구분 |
| 맥락 | visit_expectation, time_window | 예정된 방문과 비정상 시간대를 보조적으로 구분 |

*표 1. 센서 metric 명칭은 구현 과정에서 변경될 수 있으며, 변경 시 데이터 사전에 기록한다.*

### 5.2 수집하지 않거나 위험도에 사용하지 않는 정보

- 얼굴인식 결과, 주민등록번호, 정확한 성별·연령·인종·장애·외모·의복 기반 프로파일링
- 음성 대화 내용의 상시 녹음·전사, 현관 안전과 무관한 위치 이력, 주소록·통화기록
- 단순한 인상이나 추정 감정만으로 사람을 ‘위험 인물’로 분류하는 값

## 6. 위험도 평가 정책

> [!NOTE]
> **현재 상태 — 계산 로직 미정**
>
> 현재 DemoPassThroughRiskEngine은 normal 14, watch 46, warning 68, critical 88의 고정 값을 보여준다. 화면과 데이터 흐름을 확인하기 위한 값이며 algorithmVersion은 비어 있다. 실제 실증, 안전 판단, 성능 주장에는 사용하지 않는다.

### 6.1 입력과 결과의 분리

- 센서 수집 계층과 위험도 계산은 분리한다. 센서는 공통 SensorEvent만 만들고, 위험도 엔진은 SensorEvent와 Incident를 입력받는다.
- 엔진 교체 시 risk_engine_versions에 버전, 상태(draft/active/retired), 변경 이유와 검증 결과를 남긴다.
- 기존 평가를 덮어쓰지 않고 새 평가를 추가하여 발표·테스트 결과를 재현할 수 있게 한다.

### 6.2 단계별 의미와 권장 반응

| 단계 | 코드 | 정책적 의미 | 권장 반응 |
| --- | --- | --- | --- |
| 정상 | Normal | 특이 징후 없음 | 기록만 유지. 사용자 알림 없음. |
| 관심 | Watch | 약한 징후 또는 품질 낮은 단일 신호 | 대시보드 표시. 동일 상황 반복 여부 관찰. |
| 주의 | Warning | 복수 징후 또는 지속·반복 접근 | 보호자에게 확인 요청을 제안. 영상은 별도 근거와 설정이 있을 때만 확인. |
| 긴급 | Critical | 강제 개방, 수동 SOS 등 즉시 확인할 단서 | 큰 화면·진동 등 강한 알림. 거주자 연락 및 필요 시 112 신고를 사람이 결정. |

### 6.3 위험도 요소 선정 기준

위험도 산식은 아직 정하지 않았다. 데이터 없이 숫자를 먼저 확정하면 화면은 그럴듯해 보여도 근거가 약해진다. 우선 체류시간, 문과의 최소거리, 접근 반복, 충격 강도·빈도, 강제 개방, 수동 SOS, 복수 센서 일치, 예정 방문, 시간대, 최근 반복 사건을 후보로 두고 실험한다. 방향성·단위·결측 처리·오탐 가능성은 데이터 사전에 기록한다.

수동 SOS나 확실한 강제 개방은 일반 점수보다 먼저 확인해야 할 수 있다. 이를 ‘우선 확인 규칙’ 후보로 두되, 센서 고장과 오입력, 사용자 취소 절차를 함께 설계한다.

### 6.4 금지되는 자동화

- 위험도만으로 특정인을 범죄자·스토커로 단정하거나 신원·관계를 추정하는 행위
- 위험도만으로 문을 자동 잠금·해제하거나 외부인의 이동을 물리적으로 제한하는 행위
- 사용자 확인 없이 112, 보호자, 이웃 등 제3자에게 개인 데이터를 자동 전송하는 행위

## 7. 사고 처리와 알림 정책

### 7.1 처리 흐름

1. **수신:** 장치 ID, event ID, 발생시각, readings를 검증하고 중복 전송을 제거한다.
1. **정규화:** 단위와 metric을 공통 형식으로 바꾸고 원본 payload는 필요한 범위에서만 보존한다.
1. **그룹화:** 같은 주거의 진행 중 사고에서 마지막 이벤트와 2분 이내면 같은 incident로 묶는다.
1. **평가:** 활성 위험도 엔진이 있으면 버전과 근거를 기록한다. 현재는 데모 또는 pending 상태를 사용한다.
1. **표시·알림:** 단계, 요약, 시간, 장치 상태를 웹·모바일에 표시한다. 외부 전송은 수신자 동의와 설정을 확인한다.
1. **피드백·종료:** 보호자가 실제 위험, 정상 방문, 오경보, 테스트로 분류하고 사건을 종료한다.

### 7.2 알림 수신 원칙

- 거주자는 보호자별 수신 여부, 단계, 조용한 시간대를 설정할 수 있어야 한다.
- **알림 본문에는 필요한 최소정보만 포함한다:** 주거 별칭, 시간, 단계, 대표 근거, 확인 링크.
- 잠금화면 알림에는 상세 주소, 얼굴·영상 미리보기, 민감한 관계 정보를 기본 표시하지 않는다.
- 전송 실패는 재시도 횟수와 실패 사유를 남기고, 무한 반복 알림을 금지한다.

### 7.3 긴급 상황과 신고

| 상황 | 시스템·거주자 조치 | 보호자 조치 |
| --- | --- | --- |
| 즉시 위험이 의심됨 | 거주자에게 연락하거나 안전한 장소로 이동하도록 안내 | 상황을 직접 판단해 112 신고 |
| 연락 불가·정보 부족 | 현장 접근이나 대면 확인을 강요하지 않음 | 다른 보호자 확인 또는 112 상담 고려 |
| 오경보 확인 | 알림 취소 및 incident 종료 | false_alarm 피드백과 원인 기록 |
| 테스트·시연 | 화면에 TEST/DEMO 표시 | 실제 신고·대외 알림 차단 |

> [!NOTE]
> **자동 신고 제한**
>
> 캡스톤 MVP는 112에 자동 신고하지 않는다. 신고 버튼을 추가하더라도 전화 연결이나 안내부터 시작하고, 사용자가 수신자와 전송 내용을 확인한 뒤 실행하게 한다.

## 8. 개인정보·영상정보 정책

### 8.1 개인정보 처리 기본

- 처리 목적, 항목, 보유기간, 제공 대상, 삭제 방법을 테스트 참여자에게 이해하기 쉬운 언어로 사전 고지한다.
- 거주자와 보호자의 계정·연락처는 서비스 제공에 필요한 범위로 제한하고 개발 로그에서는 마스킹한다.
- 개인정보를 발표 자료에 사용할 때는 실제 주소·이름·연락처·장치 식별자를 제거하고 합성·더미 데이터를 우선한다.
- 팀원이 데이터를 내려받거나 외부 저장소로 옮겨야 할 때는 목적, 담당자, 파일 위치, 삭제 예정일을 기록한다.

| 설치 전 | 촬영 목적, 설치 근거, 대수·위치·범위, 관리책임자, 촬영시간, 보관기간, 접근자, 열람·삭제 절차를 문서화 |
| 촬영 범위 | 현관 안전에 필요한 최소 범위만 촬영하고 이웃집 내부·창문·불필요한 공용공간은 가림 영역으로 설정 |
| 안내 | 공개된 장소를 촬영하는 경우 정보주체가 쉽게 알 수 있는 안내판 등 필요한 조치를 검토 |
| 저장 | 기본 미저장 또는 이벤트 구간만 저장. 원본을 보관하면 암호화·접근기록·자동삭제 적용 |
| 분석 | 얼굴인식·신원추정·감정추정은 사용하지 않음. 연구 목적으로 필요하면 별도 검토와 승인 |
| 열람·반출 | 본인 또는 정당한 요청인지 확인하고 제3자 영상은 마스킹. 목적·범위·처리 결과 기록 |

### 8.3 정보주체의 권리

참여자는 자신의 개인정보에 대해 열람, 정정, 삭제, 처리정지, 동의 철회를 요청할 수 있다. 팀은 요청자와 대상 범위를 확인하고, 가능한 경우 10일 안에 처리 결과 또는 지연 사유를 알리는 것을 내부 목표로 둔다. 이 기간은 법정 기한을 뜻하지 않으며, 실제 서비스 전에는 관련 절차를 다시 확인한다.

### 9.1 제3자 제공과 외부 반출

- 원칙적으로 팀 내부의 승인된 구성원만 접근한다. 발표·수업 제출은 비식별 또는 더미 데이터로 한다.
- 경찰·학교·서비스 사업자 등 외부 제공 요청이 있으면 요청 주체, 법적 근거, 대상 범위, 제공 일시와 담당자를 기록하고 필요한 최소 범위만 제공한다.
- 클라우드·푸시·분석 도구를 도입할 때는 처리 위치, 재위탁, 보존기간, 삭제 방법을 확인하고 데이터 목록에 등록한다.

## 11. 운영 안정성·오경보 정책

### 11.1 장치·네트워크 이상

- 장치 last_seen_at, 배터리, 연결 상태, 센서 quality를 별도 상태로 표시하고 위험도와 혼동하지 않는다.
- 서버 시간이 아닌 센서 발생시각과 수신시각을 모두 저장하여 지연·재전송을 구분한다.
- 일부 센서가 누락된 경우 ‘정상’으로 단정하지 않고 데이터 부족 또는 장치 이상을 표시한다.
- 네트워크 단절 시 로컬 경보가 필요하다면 하드웨어 계층이 독립적으로 동작하도록 설계하고, 클라우드 결과만 신뢰하지 않는다.

### 11.2 오경보·미탐 피드백

| 라벨 | 의미 | 후속 조치 |
| --- | --- | --- |
| actual_risk | 실제 위험 또는 강한 위협 정황 | 사건 타임라인 보존, 팀 검토 |
| expected_visit | 택배·방문객 등 예정된 정상 상황 | 방문 맥락 기능 검토 |
| false_alarm | 센서 오류·환경 변화·잘못된 임계값 | 원인 분류, 장치·규칙 수정 후보 |
| test | 시연·개발 테스트 | 성능 통계에서 제외 |
| uncertain | 판단할 정보 부족 | 확정 라벨로 강제 변환하지 않음 |

### 11.3 성능 평가

위험도 엔진을 평가할 때는 정밀도, 재현율, 오경보율, 미탐률, 알림 지연, 센서 결측률을 함께 본다. 전체 정확도 하나만 높다고 해서 안전한 엔진이라고 말하지 않는다. 테스트·더미 데이터와 실제 참여자 데이터를 분리하고, 데이터 규모와 라벨 기준, 한계를 발표 자료에 같이 적는다.

## 13. 변경관리와 책임 있는 개발

### 13.1 정책·알고리즘 변경

센서 항목, 위험요소, 임계값, 알림 대상, 보존기간, 카메라, 외부 서비스가 바뀌면 버전과 이유를 남긴다. 안전이나 개인정보에 영향을 주는 변경은 코드에 넣기 전에 팀 책임자와 SW·정책 담당이 함께 확인한다.

| 등급 | 예시 | 승인 |
| --- | --- | --- |
| 경미 | 문구, 화면 순서, 비식별 더미 데이터 | 담당자 기록 후 반영 |
| 중간 | 센서 metric, 알림 규칙, 보존 자동화 | SW·정책 + HW 담당 검토 |
| 중대 | 실제 위험 산식, 카메라, 자동 제어, 외부 제공, 실제 신고 연동 | 팀 책임자 승인 + 법·학교 규정 재검토 |

### 13.2 외부 실증 전 체크리스트

- [ ] 참여자에게 목적·데이터 항목·보존기간·권리·연락처를 설명하고 동의 또는 적법한 근거를 확인했다.
- [ ] 실제 주소·이름·연락처를 더미 데이터와 분리했고 발표 화면에 노출되지 않는다.
- [ ] 사용자·보호자·관리자 권한과 장치 인증을 구현하고 다른 가구 데이터에 접근할 수 없는지 테스트했다.
- [ ] 장치 ID·키 발급, 키 폐기, 요청 서명, 중복·재전송 방지를 검증했다.
- [ ] 위험도 엔진 버전, 입력요소, 임계값, 결측 처리, 테스트 결과와 한계를 문서화했다.
- [ ] 데모·테스트 알림이 실제 보호자나 112로 전송되지 않도록 분리했다.
- [ ] 보존기간 만료 시 자동 삭제되고 백업·로그에서도 처리되는지 확인했다.
- [ ] 카메라를 쓰는 경우 설치 권한, 공개 장소 여부, 촬영범위, 안내, 영상 운영 방침을 별도 검토했다.
- [ ] 센서 고장·네트워크 단절·서버 오류 시 사용자 화면과 안전한 기본 동작을 확인했다.
- [ ] 보안·개인정보 사고 연락망과 중지·복구 절차를 팀이 알고 있다.
