# RISK-ZERO 위험도 산정 및 검증 방안

*하드웨어 후처리 결과로 무엇을 판단하고 어떻게 검증할지 정리한 초안*

| 문서 소유 | Pixel-Zero 팀 |
| --- | --- |
| 적용 범위 | 위험도 엔진 · ModuleEvent 입력 · 웹/모바일 표시 · 검증 데이터 |
| 버전 / 기준일 | v0.2 / 2026-07-27 |
| 상태 | 팀 검토용 — 계산식·가중치·임계값은 아직 확정하지 않음 |

> [!NOTE]
> **이 문서의 결론**
>
> 현재 위험도는 실제 사람을 판별하는 점수가 아니다. 하드웨어가 만든 수치형 지표를 같은 형식으로 받고, 나중에 계산 로직을 교체할 수 있게 만든 뒤, 더미 데이터와 반복 실험으로 먼저 검증한다. 사람이 확인하기 전에는 범죄 여부를 확정하거나 신고·도어락 제어를 자동 실행하지 않는다.

- 법과 연구가 공통적으로 말하는 핵심은 단발성 인상보다 접근의 지속성·반복성·위협의 상승이다.
- 센서가 직접 볼 수 있는 신호와 사용자가 알려준 맥락을 분리한다.
- 가중치와 임계값은 실험 전까지 TBD로 남기고, 현재 화면에는 더미 결과임을 표시한다.
- 오경보와 미탐을 함께 측정한다. ‘정확도 하나’로 위험도 성능을 설명하지 않는다.

## 1. 왜 위험도를 따로 설계하는가

현관 앞에서 사람이 잠시 멈춘 것과, 여러 번 돌아오거나 문을 강제로 열려고 한 것은 같은 상황이 아니다. 하지만 센서값 하나만 보면 둘을 구분하기 어렵다. 이번 프로젝트에서는 한 번의 측정값보다 시간에 따라 이어지는 행동의 흐름을 먼저 보려고 한다.

문제는 실제 위험 사건이 자주 발생하지 않는다는 점이다. 데이터가 적은 상태에서 가중치를 먼저 정하면 발표 화면은 그럴듯해 보여도 실제 근거는 약해진다. 그래서 현재 단계에서는 입력 구조와 기록 방식을 먼저 고정하고, 계산식은 교체 가능한 모듈로 남긴다.

### 1.1 이번 문서에서 말하는 위험도

| 구분 | 의미 | 이번 프로젝트의 처리 |
| --- | --- | --- |
| 위험 가능성 | 현관 주변 행동이 안전 문제로 이어질 가능성 | 반복·지속·강제성 신호로 추정 |
| 피해 크기 | 문 강제 개방, 직접 위협 등 발생 시 예상되는 영향 | 수동 SOS·강제 개방은 우선 확인 후보 |
| 판단 신뢰도 | 현재 센서값이 얼마나 믿을 만한지 | confidence·quality·센서 일치 수로 별도 표시 |

> [!NOTE]
> **중요한 구분**
>
> 위험 점수와 데이터 신뢰도는 같은 값이 아니다. 센서 품질이 낮으면 ‘정상’이 아니라 ‘판단 정보 부족’으로 표시해야 한다.

### 1.2 법·연구에서 가져온 방향

- 스토킹처벌법은 접근·따라다님·진로 방해, 주거 부근에서 기다리거나 지켜보는 행위, 지속·반복성을 중요한 행위 유형으로 본다. 이를 사람의 신원 판별이 아니라 접근·체류·반복 이벤트 설계의 근거로 사용한다. [R1]
- 미국 NIJ 문헌 검토에서는 물리적 감시가 자주 보고되는 수법이며, 친밀한 관계였던 가해자의 스토킹은 폭력·무기 사용과 더 강하게 연결될 수 있다고 정리한다. [R2]
- McEwan 외 연구에서는 과거 친밀 관계, 명시적 위협, 이전 재산 훼손이 스토킹 중 폭력과 연결되었다. 다만 이 정보는 센서가 추정하지 않고 사용자가 직접 제공한 경우에만 별도 맥락으로 다룬다. [R3]

이 근거들은 위험요소 후보를 고르는 참고자료다. RISK-ZERO가 법적 스토킹 여부나 사람의 범죄 가능성을 판정한다는 의미는 아니다.

## 2. 위험도 요소 후보

위험요소는 센서가 직접 관측하는 값, 일정 시간 동안 누적해서 계산하는 값, 사용자가 직접 입력하는 맥락, 데이터 품질의 네 층으로 나눈다. 이렇게 나누면 센서 종류가 바뀌어도 위험도 엔진의 입력 구조는 유지할 수 있다.

### 2.1 센서가 직접 관측하는 요소

| 요소 | 예시 metric | 위험 방향 | 주의할 점 |
| --- | --- | --- | --- |
| 현관 존재 | presence | 다른 신호와 함께 사용 | 존재만으로 위험 판단 금지 |
| 체류시간 | dwell_seconds | 길수록 확인 필요 | 택배·통화 등 정상 체류 존재 |
| 문과 거리 | min_door_distance_cm | 가까운 상태가 지속될수록 상승 후보 | 센서 각도·공간 크기 영향 |
| 문 충격 | impact_peak / impact_count_10s | 강도·횟수 상승 시 위험 후보 | 바람·문 닫힘과 구분 필요 |
| 문 상태 | door_state / door_open_seconds | 비정상 개방·장시간 열림 확인 | 거주자 정상 출입과 구분 |
| 손잡이·인증 실패 | handle_attempts / auth_fail_count | 반복 시 상승 후보 | 장치 오류·사용자 실수 존재 |
| 수동 SOS | manual_sos | 즉시 확인 우선 규칙 후보 | 취소·오입력·테스트 모드 필요 |

### 2.2 시간 흐름에서 계산하는 요소

| 요소 | 계산 예시 | 의미 |
| --- | --- | --- |
| 접근 반복 | approach_count_10m / 24h | 한 번보다 여러 번 돌아오는 상황을 구분 |
| 체류 반복 | dwell_episode_count | 짧은 체류가 여러 번 이어지는 패턴 확인 |
| 행동 상승 | impact·거리·체류의 최근 변화량 | 약한 신호가 강해지는 흐름 확인 |
| 동일 장소 재발 | recent_incident_count | 사람을 식별하지 않고 현관 사건의 반복만 집계 |
| 복수 센서 일치 | sensor_agreement_count | 단일 센서 오류와 동시 관측을 구분 |
| 이벤트 밀도 | events_per_minute | 짧은 시간에 행동이 집중되는지 확인 |

## 3. 사용자 맥락과 제외 항목

### 3.1 사용자가 직접 알려주는 맥락

| 맥락 | 입력 방식 | 처리 원칙 |
| --- | --- | --- |
| 예정 방문 | expected / unknown / not_expected | 정상 방문 가능성을 설명하는 보조값. 단독으로 위험을 0으로 만들지 않음 |
| 거주자 확인 | safe / needs_help / uncertain | 센서보다 높은 우선순위의 사후 라벨로 사용 |
| 이전 위협 신고 | 선택 입력 boolean + 시각 | 대화 내용을 상시 녹음하지 않고, 사용자가 직접 기록한 사실만 사용 |
| 이전 재산 훼손 | incident feedback | 문·도어락 훼손 확인 기록과 연결 |
| 보호 필요 맥락 | sensitive_context flag | 관계 종류를 추정하지 않으며 접근권한·보존기간을 더 엄격히 적용 |

> [!NOTE]
> **맥락 데이터는 선택 사항**
>
> 과거 관계, 위협, 보호조치 여부는 연구상 참고가 될 수 있지만 매우 민감하다. 이번 캡스톤에서는 자동 수집하지 않는다. 사용자가 원할 때 최소한의 boolean 값으로 입력하고, 발표 화면에는 상세 내용을 노출하지 않는 방향이 안전하다.

### 3.2 위험도에 넣지 않는 항목

| 금지·제외 항목 | 이유 |
| --- | --- |
| 성별·연령·인종·국적·장애·외모·의복 | 위험 행동이 아니라 사람의 특성을 근거로 판단하게 되며 편향 가능성이 큼 |
| 얼굴인식·신원 추정 | 현관 위험 확인에 비해 개인정보 침해가 크고, 오인식 시 피해가 큼 |
| 표정·감정 추정 | 센서·영상만으로 정확히 판단하기 어렵고 위험 행동과 직접 같지 않음 |
| 정신건강 상태 추정 | 연구 변수를 이유로 장치가 진단하거나 낙인찍어서는 안 됨 |
| 상시 음성 녹음·대화 전사 | 필요성에 비해 사생활 침해가 크며 주변 사람의 정보까지 수집될 수 있음 |
| 하나의 약한 센서 신호 | 체류·거리·소리 하나만으로는 정상 방문과 위험 상황을 구분하기 어려움 |

개인정보보호위원회 안내서는 고정형 영상정보처리기기의 설치·운영과 개인영상정보 보호를 별도로 검토하도록 안내한다. 현재 코드는 후처리 영상 수신 구조만 두고 실제 카메라는 연결하지 않는다. 실증 전에는 설치 환경과 영상 운영 정책을 다시 검토한다. [R5]

## 4. 입력 데이터 모델

하드웨어 계층이 센서 분석과 영상 후처리를 완료한다. SW는 센서 모델명이나 원본 신호에 의존하지 않고 숫자형 metric, 시각, 품질 정보와 후처리 영상 파일만 받는다. 새로운 지표를 추가할 때 DB 컬럼을 계속 늘리지 않는 것이 핵심이다.

### 4.1 공통 이벤트 구조

```text
ModuleEvent {
  eventId, deviceId, householdId, capturedAt, receivedAt,
  metrics: [{ metric, numericValue, unit, quality }],
  processedVideo: { localUri, mimeType, sizeBytes, durationMs },
  sequence, dedupeKey, schemaVersion, isTest
}
```

### 4.2 위험도 엔진 입력·출력

```text
RiskInput { incidentId, windowStart, windowEnd, sensorEvents, contextFlags }

RiskAssessment {
  score, level, engineVersion, status, reasons,
  factorObservations, dataReliability, createdAt
}
```

| 필드 | 필수 여부 | 설명 |
| --- | --- | --- |
| metric / numericValue / unit | 필수 | 하드웨어가 분석한 수치를 같은 이름과 단위로 전달 |
| quality | 선택 | good / degraded / missing / invalid |
| capturedAt / receivedAt | 필수 | 실제 발생과 서버 수신 지연을 구분 |
| schemaVersion | 필수 | 센서 구조 변경 시 호환성 관리 |
| isTest | 필수 | 더미·시연 데이터를 실제 통계에서 분리 |

> [!NOTE]
> **현재 DB와 연결**
>
> 모바일 SQLite v3의 sensor_events와 sensor_readings가 후처리 이벤트와 수치형 지표를 저장하고, processed_videos는 앱 파일 경로를 기록한다. incidents가 시간 구간을 묶고, risk_assessments에는 DEMO 또는 pending 결과를 남긴다. 웹 D1에는 risk_engine_versions와 risk_factor_observations가 별도로 설계되어 있다.

## 5. 계산 로직 자리와 더미 엔진

가중치와 임계값은 아직 정하지 않았다. 코드에서는 인터페이스만 고정하고, 현재는 DemoPassThroughRiskEngine이 더미 점수를 반환한다. 이후 실험 결과가 나오면 같은 인터페이스를 구현하는 실제 엔진으로 교체한다.

### 5.1 계산식 자리

```text
baseScore = Σ(weight[i] × normalizedFactor[i])        # weight[i] = TBD
adjustedScore = baseScore × dataReliability + contextAdjustment
level = threshold(adjustedScore)                     # thresholds = TBD

if manual_sos or confirmed_forced_entry:
    apply_priority_review_rule()                     # 세부 규칙 = TBD
```

- 가중치와 임계값은 코드에 임시 숫자로 숨겨두지 않고 설정 파일·DB의 draft 버전으로 관리한다.
- 결측 센서를 0점으로 처리하지 않는다. 계산 가능, 정보 부족, 장치 이상을 구분한다.
- 우선 확인 규칙도 무조건 긴급 확정이 아니다. 강한 알림과 사람의 확인을 앞당기는 규칙이다.
- 동일한 사건을 새 엔진으로 다시 계산하더라도 기존 결과를 덮어쓰지 않는다.

### 5.2 현재 데모 결과

| 단계 | 더미 점수 예시 | 화면 의미 | 실제 대응 사용 |
| --- | --- | --- | --- |
| Normal | 14 | 정상 카드·그래프 확인 | 사용 금지 |
| Watch | 46 | 관심 단계 UI 확인 | 사용 금지 |
| Warning | 68 | 주의 알림 흐름 확인 | 사용 금지 |
| Critical | 88 | 긴급 화면·진동 표현 확인 | 사용 금지 |

> [!NOTE]
> **DEMO 표시 원칙**
>
> 웹과 모바일 화면에는 DEMO 또는 TEST 표시를 유지한다. algorithmVersion이 비어 있거나 engine status가 draft이면 실제 안전 판단으로 사용할 수 없게 한다.

모바일 기기 알림도 같은 DEMO 결과를 사용할 수 있으므로 발표·테스트 기기에서만 켠다. 기본 알림 설정은 주의 꺼짐, 경고·고위험 켜짐이고 같은 단계는 10분 동안 반복하지 않는다. 이 동작은 위험도 검증 결과가 아니라 알림 인터페이스 검증용이다.

## 6. 위험 단계와 사람의 대응

단계는 센서가 사람을 평가하는 등급이 아니라, 사용자가 어느 정도 빨리 상황을 확인해야 하는지 보여주는 표시다. 실제 신고나 도어락 제어는 단계만으로 자동 실행하지 않는다.

| 단계 | 의미 | 화면·알림 | 사람의 대응 |
| --- | --- | --- | --- |
| 정상 | 특이 신호가 없거나 정상 방문으로 확인 | 기록만 유지 | 별도 행동 없음 |
| 관심 | 약한 단일 신호 또는 반복 여부를 더 봐야 함 | 대시보드 표시 | 추가 이벤트 관찰 |
| 주의 | 복수 신호, 반복·지속·상승 패턴 | 보호자 확인 요청 제안 | 거주자에게 안전하게 연락 |
| 긴급 | 수동 SOS, 강제 개방 등 즉시 확인 단서 | 강한 알림·화면 강조 | 사람이 상황 확인 후 필요 시 112 신고 |
| 정보 부족 | 센서 결측·시간 지연·품질 저하 | 장치 이상 표시 | 위험 없음으로 단정하지 않음 |

### 6.1 사건 처리 흐름

| 순서 | 처리 | 남겨야 할 기록 |
| --- | --- | --- |
| 1 | 이벤트 스키마·시각·중복 여부 확인 | eventId, schemaVersion, 수신 오류 |
| 2 | 같은 주거의 근접 이벤트를 incident로 그룹화 | windowStart, windowEnd, 연결 eventId |
| 3 | draft 또는 active 엔진 실행 | engineVersion, 입력요소, 결측 처리 |
| 4 | 단계·이유·데이터 품질을 웹/모바일에 표시 | score, level, reasons, reliability |
| 5 | 사용자·보호자가 상황을 확인하고 피드백 | safe, actual_risk, false_alarm, test, uncertain |
| 6 | 사건 종료 후 오경보·미탐 원인 검토 | 조치, 담당자, 개선 후보 |

> [!NOTE]
> **자동화 제한**
>
> 위험도만으로 사람을 스토커·범죄자로 단정하지 않는다. 사용자 확인 없이 112·이웃·보호자에게 상세 개인정보를 자동 전송하지 않으며, 문을 자동 잠금·해제하는 기능도 캡스톤 범위에서는 제외한다.

현재 모바일의 사건 카테고리·오탐·중요 표시·메모는 기록 검색과 사후 검토를 위해 구현했다. 이 값을 학습·성능평가 라벨로 쓰려면 최소 2인의 검토 또는 명확한 라벨 기준을 적용하고, 불확실한 사례는 강제로 정상·위험으로 나누지 않는다.

## 7. 검증 데이터와 실험 시나리오

실제 사건 데이터를 바로 구하기 어렵기 때문에 먼저 재현 가능한 시나리오를 만든다. 같은 시나리오를 여러 사람이 여러 환경에서 반복하고, 하드웨어 후처리 수치·영상, 엔진 결과, 사람의 정답 라벨을 분리해서 저장한다.

### 7.1 기본 시나리오

| ID | 시나리오 | 기대 라벨 | 확인할 요소 |
| --- | --- | --- | --- |
| S01 | 택배 기사가 20초 머물고 떠남 | normal / expected | 짧은 체류, 예정 방문 |
| S02 | 방문자가 2분 이상 기다리지만 충격 없음 | watch / uncertain | 체류, 품질, 맥락 |
| S03 | 10분 안에 세 번 접근했다가 떠남 | watch~warning 후보 | 접근 반복, 이벤트 밀도 |
| S04 | 문을 여러 번 강하게 두드림 | warning 후보 | impact 강도·빈도 |
| S05 | 손잡이 조작과 인증 실패가 반복됨 | warning 후보 | handle/auth 반복 |
| S06 | 충격 뒤 비정상 문 열림 | critical 후보 | 강제 개방, 센서 일치 |
| S07 | 거주자가 수동 SOS를 누름 | critical 후보 | 우선 확인 규칙 |
| S08 | 센서 일부가 끊긴 상태에서 사람이 접근 | insufficient | 결측 처리, fail-safe |
| S09 | 테스트 이벤트가 실제 알림 채널로 들어감 | test | 데모 분리, 대외 알림 차단 |

### 7.2 캡스톤 수준의 반복 계획

| 항목 | 권장 시작값 | 이유 |
| --- | --- | --- |
| 반복 횟수 | 시나리오별 20회 이상 | 초기 비교가 가능한 최소한의 반복 확보 |
| 참여 조건 | 사람 3명 이상, 거리·속도 변화 | 한 사람의 움직임에만 맞는 규칙 방지 |
| 환경 조건 | 낮/밤, 문 열림/닫힘, 네트워크 지연 | 실제 사용 조건의 차이 확인 |
| 데이터 분리 | 조정용 70% / 최종 확인용 30% | 같은 데이터로 맞추고 평가하는 문제 완화 |
| 블라인드 라벨 | 가능하면 엔진 결과를 보지 않고 정답 기록 | 결과에 맞춘 사후 판단 방지 |

## 8. 평가 지표와 통과 기준

위험 사건은 정상 상황보다 훨씬 적을 수 있다. 이때 전체 정확도만 보면 대부분을 정상으로 판단하는 엔진도 좋아 보일 수 있다. NIST AI RMF도 예상 사용 조건을 반영한 시험세트, 오탐·미탐, 신뢰성, 지연과 한계를 함께 문서화하도록 제안한다. [R4]

### 8.1 반드시 같이 볼 지표

| 지표 | 질문 | 이번 프로젝트의 사용 |
| --- | --- | --- |
| 재현율(Recall) | 실제 위험 시나리오를 얼마나 놓치지 않았는가? | 미탐 관리의 핵심 |
| 정밀도(Precision) | 위험으로 알린 것 중 실제 위험은 얼마나 되는가? | 불필요한 알림 피로 확인 |
| 오경보율 | 정상 시나리오를 위험으로 본 비율은? | 택배·방문객 구분 확인 |
| 미탐률 | 위험 시나리오를 정상으로 본 비율은? | 가장 위험한 실패 유형 확인 |
| 알림 지연 | 발생 후 화면·알림까지 얼마나 걸렸는가? | 실시간성 확인 |
| 결측률 | 필요한 후처리 지표가 없는 사건은 얼마나 되는가? | 장치·네트워크 품질 확인 |
| 단계 일치 | 같은 시나리오에서 결과가 안정적으로 나오는가? | 규칙의 재현성 확인 |

### 8.2 active 전환 조건

- [ ] 시나리오와 라벨 기준을 팀 문서로 고정했다.
- [ ] 엔진 버전, 가중치, 임계값, 결측 처리와 변경 이유를 기록했다.
- [ ] 조정에 쓰지 않은 데이터에서 오경보·미탐·지연을 다시 확인했다.
- [ ] 필요한 지표가 빠지거나 지연될 때 정상으로 오판하지 않는지 확인했다.
- [ ] 결과에 대표 근거와 데이터 품질을 함께 표시한다.
- [ ] 실제 하드웨어·실제 사용자 연결 전 정책 문서와 개인정보 처리 범위를 다시 승인했다.

> [!NOTE]
> **수치 목표는 아직 TBD**
>
> 이번 초안은 평가 방법을 먼저 정한다. 재현율 몇 %, 오경보율 몇 %처럼 최종 통과 수치는 파일럿 데이터를 본 뒤 팀과 지도교수가 정한다. 데이터 없이 목표 숫자를 먼저 확정하지 않는다.

## 9. 개발 순서와 담당 작업

하드웨어 후처리 방식과 계산 로직이 아직 바뀔 수 있으므로, SW는 데이터 계약과 기록 구조부터 고정한다. 아래 순서로 진행하면 수치형 지표가 추가돼도 전체 구조를 다시 만들 필요가 없다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | ModuleEvent 계약 확정 | 수치형 metrics, 영상 메타데이터, sequence 예제 작성 |
| 2 | 모듈 동기화 검증 강화 | 중복 eventId, 잘못된 수치·시각·파일 크기 오류 처리 |
| 3 | incident 그룹화 규칙 구현 | 2분 기본 창을 설정값으로 분리하고 테스트 작성 |
| 4 | RiskEngine 인터페이스 고정 | 더미 엔진과 실제 엔진이 같은 입출력 사용 |
| 5 | factor observation 저장 | 결과마다 사용 요소·값·신뢰도·근거 이벤트 기록 |
| 6 | 시나리오 더미 데이터 생성 | S01~S09를 API와 DB에서 재현 가능 |
| 7 | 웹·모바일에 근거 표시 | 점수, 단계, DEMO, 대표 이유, 데이터 품질 표시 |
| 8 | 피드백 API 구현 | safe / actual_risk / false_alarm / test / uncertain 저장 |
| 9 | 평가 스크립트 작성 | precision, recall, 오경보, 미탐, 지연 보고서 생성 |
| 10 | active 승인 절차 연결 | draft 결과 검증 후 승인된 버전만 active 가능 |

### 9.1 현재 구현 반영

| 항목 | 상태 | 다음 작업 |
| --- | --- | --- |
| ModuleEvent·ModuleGateway 계약 | 구현 | HW 담당과 metric 이름·단위·영상 파일 전달 방식 확정 |
| sequence·ACK·중복 방지 | 메모리 모듈과 SQLite 구현 | 실제 BLE/Wi-Fi에서 재연결·유실 시험 |
| 영상 파일 저장 | 복사·크기 확인·500MB 정리 구현 | 실제 파일, 체크섬, 손상 파일 시험 |
| 위험도 엔진 | 인터페이스 자리와 DEMO 고정값 | factor 목록·가중치·임계값 실험 후 draft 엔진 |
| 이벤트 조회·분류 | 캘린더·검색·카테고리·오탐·메모 구현 | 검증용 라벨 변환 기준 확정 |
| 기기 알림 | 단계별 설정·10분 제한·중복 방지 구현 | 실제 이벤트에서 지연·누락 측정 |
| 평가 스크립트 | 미구현 | precision, recall, 오경보, 미탐, 지연 산출 |

### 9.2 정책 담당 체크

- [ ] 실험 참여자에게 목적, 수집 항목, 보존기간, 삭제 방법을 설명한다.
- [ ] 더미·테스트 데이터와 실제 참여자 데이터를 DB와 화면에서 분리한다.
- [ ] 관계·위협 등 민감 맥락은 선택 입력으로 두고 최소한으로 저장한다.
- [ ] 실제 카메라를 연결하기 전에 설치 환경, 촬영 범위, 후처리 영상 운영 방침을 다시 검토한다.
- [ ] 문서 버전과 코드의 engineVersion이 맞는지 발표 전 확인한다.

## 10. 한계와 참고 근거

### 10.1 현재 한계

- 현재 점수와 단계는 더미 값이며, 실제 위험을 예측하도록 검증되지 않았다.
- 현관 센서만으로 사람의 의도, 관계, 위협의 맥락을 정확히 알 수 없다.
- 같은 행동도 공동주택·단독주택, 택배 환경, 문 구조에 따라 다르게 측정될 수 있다.
- 실제 위험 사건이 적기 때문에 시나리오 실험 성능이 현실 성능을 그대로 보장하지 않는다.
- 이 문서는 캡스톤 내부 설계 기준이며 법률 자문이나 수사기관의 위험평가를 대체하지 않는다.
