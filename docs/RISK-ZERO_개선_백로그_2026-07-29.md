## 다음 P0 작업

아래 순서대로 진행한다. 앞의 결정이 끝나야 뒤의 데이터 계약을 고정할 수 있다.

1. **위험도 계산 위치 확정**
   - ESP32 계산 또는 모바일 계산 중 하나를 팀에서 선택
   - 선택 결과에 맞춰 `ModuleEvent`와 DB 필드 확정
2. **실제 통신 방식 확정**
   - BLE와 Wi-Fi 중 중간발표 기본 경로 선택
   - 연결 끊김, 재연결, ACK, 백그라운드 제한 시험
3. **하드웨어 metric 사전 확정**
   - PIR, 진동, 리드 스위치의 metric 이름·단위·범위·품질값 정의
   - 잘못된 값과 결측값 처리 기준 작성
4. **최소 `ModuleGateway` 어댑터**
   - ESP32 메시지를 기존 `ModuleEvent`로 변환
   - 더미 경로와 실제 경로를 화면에서 구분
5. **FPGA 신호 계약**
   - request, approve, risk level, fault, heartbeat, timeout, reset 기본값 정의
   - FPGA가 실제로 검증할 수 있는 범위만 발표 문구에 사용
6. **수직 통합 시험**
   - 센서 또는 버튼 → ESP32 → 모바일 저장·표시 → FPGA LED 출력
   - 정상·위험·중복·통신 단절·reset 시나리오 반복

## 팀 회의에서 먼저 결정할 내용

| 결정 | 선택지 | 결정 전에는 하지 않을 작업 |
| --- | --- | --- |
| 위험도 계산 | ESP32 / 모바일 | 위험도 필드·엔진 구현 |
| 모바일 통신 | BLE / Wi-Fi | 실제 `ModuleGateway` 구현 |
| FPGA 역할 | 필수 Safety Gate / 추가 시연 | 최종 신호·FSM 범위 확정 |
| 중간발표 출력 | LED / 서보 / 솔레노이드 | 구동 회로·하우징 제작 |
| P0 센서 | PIR·진동·리드 스위치 등 | BOM 확정과 대량 구매 |
| 카메라 | 포함 / 제외 | 실제 영상 입력·보존 시험 |

## 완료 기준

- 이벤트 100회 반복 시 sequence 누락·중복·ACK 복구 결과를 기록한다.
- DEMO 결과와 실제 하드웨어 결과를 화면과 DB에서 구분한다.
- 통신 단절·reset·모순 신호에서는 FPGA 출력이 기본 0이 된다.
- 감지부터 앱 표시와 출력까지 평균·최대 반응시간을 측정한다.
- Android 제스처 내비게이션과 3버튼 내비게이션에서 상·하단 UI가 겹치지 않는다.
- 새 APK는 위 항목 중 배포 대상 수정이 모인 뒤 버전과 `versionCode`를 함께 올린다.
