# RISK-ZERO 제품 개발계획 검토 및 수정 권고

- 검토일: 2026-07-28
- 검토 대상: `Risk-Zero_팀공유용_제품_개발계획_총정리.docx`
- 저장소 기준: Mobile v0.2.0, `main` 커밋 `c20d1619`
- 목적: 계획서의 제품 방향을 현재 구현과 일치시키고, 팀 회의에서 확정해야 할 기술·일정·안전 항목을 정리한다.

## 1. 결론

계획서는 제품 목표와 FPGA Safety Gate의 시연 가치를 이해하기 쉽게 정리했다. 특히 방문자 입력과 집주인 제어 권한을 분리하고, 위험도를 문 개방 권한으로 사용하지 않으며, 조건이 불완전할 때 출력을 차단한다는 방향은 유지할 가치가 있다.

다만 현재 문서는 FPGA·ESP32·잠금장치 중심의 신규 구조를 이미 확정되거나 구현된 제품처럼 설명한다. 실제 저장소는 모바일·웹 MVP가 먼저 구현된 상태이며, 실제 위험도 계산식, 하드웨어 통신 어댑터, 사용자 인증, 원격 보호자 알림, 도어락 제어는 아직 없다. 따라서 계획서를 팀 기준 문서로 사용하려면 다음 세 상태를 명확히 분리해야 한다.

1. 현재 구현 완료
2. 팀 합의가 필요한 신규 제안
3. 구현·검증 후에만 사용할 수 있는 기능

## 3. 계획서에서 반드시 수정할 사항

### 3.1 구현 상태와 목표 상태를 분리한다

계획서의 `센서 → ESP32 위험도 계산 → FPGA 검사 → 잠금장치·카메라·알림` 흐름은 현재 동작하는 구조가 아니라 신규 목표 구조다. 각 기능과 표에 다음 상태 중 하나를 표시한다.

- `완료`
- `구현 중`
- `계획`
- `결정 필요`
- `제외`

권장 표기 예시:

| 기능 | 현재 상태 | 다음 작업 |
| --- | --- | --- |
| 모바일 이벤트 조회·저장 | 완료 | 실제 모듈 이벤트 연결 |
| 로컬 위험 알림 | 완료, DEMO 입력 기준 | 실위험도 결과 연결 |
| 위험도 엔진 | 계획 | 계산 위치·가중치·임계값 확정 |
| FPGA Safety Gate | 신규 제안 | 위협 모델·신호 계약·FSM 검증 |
| 앱 사용자 인증 | 미구현 | 데모 인증과 실제 인증 범위 구분 |
| 원격 보호자 알림 | 미구현 | 서버·계정·푸시 구조 설계 |
| 문 모형 제어 | 신규 제안 | 안전 회로와 시연 범위 승인 |
| 실제 도어락 제어 | 제외 | 안전·책임 검토 후 별도 과제 |

### 3.2 위험도 계산의 소유 위치를 결정한다

계획서는 ESP32가 위험도를 계산한다고 확정하지만, 현재 저장소는 하드웨어에서 수치형 metric과 영상을 받아 소프트웨어의 `RiskEngine`에서 평가하는 방향이다. 현재 `ModuleEvent` 계약에도 ESP32가 계산한 위험도 결과를 전달하는 필드가 없다.

팀은 다음 중 하나를 선택해야 한다.

#### 안 A: ESP32에서 계산

- `ModuleEvent`에 `riskScore`, `riskLevel`, `reasons`, `engineVersion`, `policyVersion`, `evaluatedAt` 추가
- 모바일은 전달받은 결과와 근거를 저장·표시
- 펌웨어 알고리즘 버전과 재현 방법 관리

#### 안 B: 모바일에서 계산

- ESP32는 정규화된 metric과 품질·시각 정보만 전달
- 모바일 `RiskEngine`이 위험도를 계산
- 가중치·임계값을 앱 또는 버전 설정으로 관리

위 결정을 내리지 않은 상태에서 ESP32와 앱을 병행 개발하면 이벤트 계약과 DB 저장 구조가 다시 바뀔 가능성이 크다.

### 3.3 FPGA 보안 주장과 위협 모델을 좁힌다

현재 계획은 앱 인증·승인 상태가 ESP32를 거쳐 FPGA로 전달되는 구조다. 이 경우 FPGA는 `auth=1`, `approve=1`이라는 신호가 실제 인증 결과인지 독립적으로 확인하지 못한다. ESP32 자체가 공격당했다고 가정하면 인증·승인 플래그도 위조될 수 있다.

따라서 기본 시연 문구는 다음 수준으로 제한하는 것이 정확하다.

> FPGA Safety Gate는 누락·모순·만료·통신 단절이 있는 개방 요청을 독립적으로 차단한다.

다음 표현은 별도 인증 구조가 없으면 사용하지 않는다.

- `ESP32가 해킹돼도 FPGA가 방어한다`
- `FPGA가 앱 인증을 독립적으로 검증한다`
- `FPGA이므로 해킹이 불가능하다`

ESP32 침해까지 위협 모델에 포함하려면 앱 또는 신뢰 경로가 생성한 서명/MAC, nonce, 만료시간을 FPGA가 직접 검증해야 한다. 이 기능은 Arty A7 자원, 개발 기간, 키 저장 방식을 확인한 뒤 범위를 결정한다.

### 3.4 FPGA–ESP32 신호 계약을 문서화한다

최소 신호 계약에 아래 항목을 포함한다.

- 신호명, 방향, 비트 폭, active high/low
- `request`, `approve`, `risk_level`, `door_state`, `sensor_fault`
- heartbeat 주기와 timeout
- 요청 nonce 또는 sequence
- 요청 유효시간
- reset·전원 복구 시 기본 상태
- 차단 사유 코드
- 허가 펄스 최대 폭
- fault latch와 해제 조건
- ESP32와 Arty A7의 3.3V 로직 호환 및 접지 방식

버튼과 LED만 사용하는 초기 시연도 이 계약과 동일한 신호를 사용해야 센서·앱으로 교체할 때 FSM을 다시 만들지 않는다.

### 3.5 기존 앱과 데이터 구조를 재사용한다

앱 개발 프레임워크는 미결정 사항이 아니다. 현재 Expo·React Native 앱을 유지하고 하드웨어 연결 계층만 추가하는 것이 기본안이다.

앱 담당 작업은 다음처럼 수정한다.

- Android 하단 시스템 UI 가림 이슈 수정
- BLE 또는 Wi-Fi `ModuleGateway` 어댑터 구현
- ESP32 메시지를 기존 `ModuleEvent`로 변환
- 기존 SQLite·영상 저장·알림·이벤트 화면에 실제 데이터 연결
- 승인 요청의 유효시간, 중복 방지, 재전송 규칙 구현
- 데모 승인 UI와 실제 사용자 인증을 명확히 구분

## 4. 부품·회로 계획 수정

### 4.1 솔레노이드와 서보를 같은 회로로 취급하지 않는다

둘 중 하나를 중간발표 출력으로 먼저 확정한다.

#### 솔레노이드 선택 시

- 정격 전압·정상 전류·돌입 전류
- logic-level N-MOSFET
- 플라이백 다이오드
- 게이트 직렬 저항과 풀다운 저항
- 퓨즈 또는 전류 제한
- 12V 전원 용량
- 저전압 제어부와의 공통 접지 또는 절연
- 고전류 경로의 브레드보드 사용 금지

#### 서보 선택 시

- PWM 제어
- 별도 5~6V 전원
- 최대 stall current
- ESP32 또는 FPGA의 PWM 소유권
- 전원 노이즈와 접지 검토

### 4.2 BOM에 실행 정보를 추가한다

| 항목 | 필수 정보 |
| --- | --- |
| 정확한 모델 | 보드·센서·액추에이터 부품 번호 |
| 수량 | 본품과 예비품 구분 |
| 단가·합계 | 배송비 포함 |
| 전압·전류 | 정상·최대값 |
| 구매처 | 주문 링크와 주문자 |
| 납기 | 예상 도착일 |
| 대체품 | 품절 또는 동작 실패 시 교체안 |
| 담당자 | 수령·보관·검수 책임 |

현재 우선순위 표에서는 mmWave/ToF가 P1인데 최초 구매 필수 목록에도 들어가 있다. P0 센서 3종을 무엇으로 볼지 먼저 통일한다.

## 5. 권장 개발 우선순위

### P0 — 중간발표 전에 반드시 연결

- 기존 모바일 앱의 하단 UI 이슈 수정
- PIR·진동·리드 스위치 입력 또는 동일 신호를 만드는 버튼 시뮬레이터
- ESP32 이벤트 정규화와 `ModuleEvent` 계약 확정
- 모바일 `ModuleGateway` 최소 어댑터
- 위험도 계산 위치 확정과 DEMO/실제 결과 구분
- ESP32–FPGA 신호 계약
- FPGA Default Deny FSM과 testbench
- LED 또는 저위험 액추에이터를 이용한 허가·차단 시연
- 정상·위험·통신 단절·reset·모순 신호 시험

### P1 — 최종 시연 경쟁력

- mmWave 또는 ToF 체류 감지
- 안전 회로가 포함된 문 모형 액추에이터
- 실제 후처리 영상 입력과 선택적 카메라
- 위험 이유·알고리즘 버전 로그
- 원격 보호자 알림의 최소 실험
- 반복 시험 결과와 오경보·미탐·반응시간 표

### P2 — 시간이 남을 때

- 앱 또는 현관 STT
- TTS 상세 안내
- 방문 일정
- 암호화 evidence packet
- BLE 서브 센서

### 제외

- 화자분리를 문 개방 인증으로 사용
- LLM이 직접 문 개방
- 실제 112 자동 신고
- 상용 도어락 리버스엔지니어링
- 실제 주거 출입문 제어

## 6. 시험과 완료 기준

`동작함`만으로 완료하지 않고 정량 기준을 남긴다.

| 영역 | 최소 확인 항목 |
| --- | --- |
| FPGA 차단 | 미인증·미승인·만료·고위험·통신 단절·reset 요청 차단 |
| 정상 허가 | 모든 조건이 맞을 때만 제한된 시간 동안 출력 |
| 이벤트 전달 | sequence 누락·중복·재전송·ACK 복구 |
| 위험도 | DEMO와 실제 엔진 결과 분리, 엔진 버전 기록 |
| 알림 | 동일 이벤트 중복 방지, 단계별 반복 제한 |
| 반응시간 | 감지부터 앱 표시·FPGA 출력까지 구간별 측정 |
| 안전 | 전원 차단·재부팅·케이블 분리 시 기본 잠금/출력 0 |

권장 결과표:

- 시나리오별 반복 횟수
- 허가율과 차단률
- 오경보율과 미탐률
- 평균·최대 반응시간
- 누락·중복 이벤트 수
- 카메라 작동 비율
- 실패 원인과 재현 절차

## 7. 개인정보·안전 범위

카메라와 문 제어를 추가하면 현재 소프트웨어 MVP보다 책임 범위가 커진다.

- 실제 주소·실제 사용자 데이터 대신 더미 데이터를 우선 사용
- 카메라는 사건 구간 또는 사용자 요청 시에만 사용
- 현재 구현된 500MB 용량 정리와 제안된 7일 보존 정책을 구분
- 원격 보호자 알림에는 주소·영상·민감정보를 기본 노출하지 않음
- 실제 도어락이 아닌 운반 가능한 문 모형에서만 액추에이터 시연
- 전원·통신·reset 오류 시 출력 0과 안전한 기계 상태 유지
- 실제 설치·외부 실증 전 사용자·장치 인증과 요청 서명 구현

## 8. 역할표 수정 제안

| 역할 | 수정 권장 산출물 |
| --- | --- |
| FPGA·통합 | 신호 계약, FSM, testbench, fault matrix, 허가·차단 로그 |
| ESP32·센서 | metric 정의, 센서 품질, 이벤트 sequence, ModuleEvent 변환 |
| 전원·구동 | 회로도, 전류 예산, 부품 정격, 보호회로, 안전 커버 |
| 앱·로그 | 기존 Expo 앱 통합, ModuleGateway, 승인 만료·중복 처리, UI 이슈 수정 |

## 10. 회의에서 먼저 확정할 결정

1. FPGA Safety Gate가 대회 최종 제품의 필수 핵심인지
2. 위험도 계산을 ESP32와 모바일 중 어디서 수행할지
3. 앱 승인 신호를 데모 플래그로만 사용할지, 실제 인증까지 구현할지
4. ESP32–FPGA가 방어하려는 오류·공격 범위
5. 중간발표 액추에이터를 LED, 서보, 솔레노이드 중 무엇으로 할지
6. P0 센서 3종과 정확한 부품 모델
7. BLE와 Wi-Fi 중 실제 모바일 통신 방식
8. 카메라를 최종 범위에 포함할지
9. 부품 구매·검수·장비 보관 책임자
10. 첫 전체 수직 통합 날짜와 반복 시험 시작일

## 11. 권장 제품 정의

현재 구현과 신규 제안을 함께 반영하면 다음 표현이 가장 안전하다.

> RISK-ZERO는 현관 센서와 후처리 결과를 기록·분류하고 위험 상황 확인을 돕는 모바일 중심 안전 보조 시스템이다. 실제 하드웨어 통신과 위험도 엔진을 연결하며, FPGA Safety Gate는 팀 승인 후 문 모형의 고위험 출력에서 불완전한 요청을 차단하는 추가 안전 계층으로 검증한다.

이 정의는 이미 구현된 모바일·데이터 기능을 보존하면서 FPGA 중심 신규 개발을 계획 상태로 정확히 구분한다.
